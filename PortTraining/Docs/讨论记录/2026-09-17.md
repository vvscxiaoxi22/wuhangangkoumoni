# 2026-09-17 讨论记录

## 堆场-箱位-集装箱-吊具最小完整闭环：设计定型与部分实现

### 背景

用户提出今晚的目标收敛为"堆场—箱位—集装箱—吊具操作"的最小完整闭环：优先做"一个箱从源箱位被选中、抓取、搬运、落到目标箱位并正确更新占用状态"的完整闭环。现有吊具物理、训练模式和HUD能复用，但两个真实集装箱模型还没接入运行时`ActiveContainer`，堆场也缺少正式的箱位/占用管理。

探查发现工作区里已经有大量本会话之前没有上下文的新内容（大概率是用户在Unity Editor里自行导入的）：`Assets/Prefabs/40尺.prefab`、`Assets/Models/集装箱/20寸集装箱.fbx`/`40寸集装箱.fbx`、`Assets/Prefabs/设备/堆场.prefab`等真实模型，以及一整套独立的港口场景资产（`Assets/Scenes/港口场景.unity`等，33000+ GameObject规模）。用`AskUserQuestion`确认：今晚要接的两个真实集装箱是40尺和20尺；堆场/箱位模型要从这套新资产里取；今晚范围先出方案不写代码，用户确认后再实现。

### 设计定型过程（多轮讨论，逐步收敛）

1. **核心架构**：全程只有一个真正物理活跃的箱子。堆场里的箱子默认静态视觉（真实FBX，无Rigidbody，但要有真实碰撞体），唯一"正在被操作"的那个箱子按阶段切换物理状态。

2. **抓取判定——一度纠结要不要用碰撞检测，最终定为物理引擎射线传感器**：
   - 最初提出"选箱在进场景前预选，不做3D场景内点选"，被用户的追问("自由模式下怎么训练")推翻——自由练习本来就没有"进场景前"这一步，选箱机制必须是物理位置驱动的：走到哪、对准哪，就是在抓哪个箱子。
   - 用户进一步要求"不能用纯计算，要回归物理引擎"，明确"四个锁应该有传感器（射线或碰撞）判断锁孔"。最终定为：吊具四个`Twistlock_FL/FR/RL/RR`点朝下发射线，命中箱子身上的锁孔碰撞体才算对齐；命中哪个箱子的锁孔就是在锁哪个箱子，堆场"选箱"和"对位"合并成同一次物理查询，不需要额外的选箱UI或距离数据库。
   - 箱型（20/40尺）跟吊具尺寸的联锁：用户明确"箱型肯定要跟吊具联锁"。四个射线点的位置需要跟着`CurrentSpreaderSize`(Ft20/Ft40)在两组坐标间切换。

3. **叠箱稳定性判断——同样经历了一次修正**：
   - 最初提出"解锁时检查对位精度决定稳不稳"，被用户纠正："跟锁箱没有关系，是落箱以后的是否会引发的问题"——不该由我们在解锁那一刻算对位算出来，而是箱子放下去之后交给PhysX真实模拟决定会不会倒。这与项目现有的"不安全解锁真实坠落"机制（本会话更早、2026-09-09那轮工作）是同一套哲学，直接复用，不用重新设计。
   - "不能从堆的中间/底部抽箱子"：用户指出只要堆场箱子有真实碰撞体，吊具物理上下降不到下面箱子的高度就会先被上面那个箱子挡住，是物理自然产生的限制，不需要单独写业务规则检查。

4. **搬运途中防穿透**：用户指出现在集装箱没有物理特性，抓箱移动时飞得太低会直接穿过其他箱子。查代码确认根源——`TryLockContainer()`锁箱那一刻`containerCollider.enabled = false`，搬运全程箱子在物理世界里完全不存在。

### 实际实现（本会话已完成的部分，详见YC-YARD-01任务契约第3节）

- 新建`YardCraneContainer.cs`扩展：`TopCornerLocalOffset`按箱型真实尺寸算四个顶角，`EnsureLockHoleColliders()`在`Awake()`自动生成四个锁孔触发碰撞体，放在新增的`ContainerLockHole`物理层（`ProjectSettings/TagManager.asset`第7槽位）。
- 新建`YardCraneYardSlot.cs`：箱位数据组件，占用状态每次进场景从`initialOccupant`重置，不持久化。
- `YardCraneEightRopeMaxPrototypeRig.cs`：`ComputeContainerCornerAlignment()`整体从纯几何距离计算换成射线版本；新增`ApplyTwistlockPositionsForSpreaderSize()`让四个射线点跟着吊具尺寸切换位置；`IsContainerAlignedForLock()`新增吊具尺寸过渡态拦截和箱型/尺寸不匹配的明确拒绝（`[YC_CONTAINER_TYPE_SPREADER_SIZE_MISMATCH]`）；`TryLockContainer()`内部原本重复的对齐判断改成统一调用`IsContainerAlignedForLock()`。

**一个需要记录的行为改变**：`YardCraneContainer`组件从"可选、不装不影响现状"变成了"锁箱能不能工作的硬性前提"——没有锁孔碰撞体，射线永远打不到东西。场景里`ActiveContainer`如果还没被加上这个组件，锁箱会持续失败并打印`[YC_CONTAINER_LOCK_HOLES_MISSING]`。

## 教师"任务考核"发布 → 学生"任务考核"接收：补上第一段链路

### 背景

用户问"教师发布任务-学生完成任务这个任务系统我们闭环了吗"。查代码确认没有闭环：教师端`SaveTaskDraftNotice()`（`YardCraneTeacherSideShell.cs`）点"创建本机草稿"只更新一行状态文字，什么都没写盘；学生端`OpenAssessment()`（`YardCraneStudentSideShell.cs`）点"任务考核"进去的是硬编码的固定练习（标题"本地模拟考核·装卸作业"），不读取任何教师端数据——两边完全独立。

用户明确这次要接的是"教师端任务考核模式 → 学生端任务考核入口"这一段（不是"实训练习"模式，也不是教师弹窗里其余5类跟单项/联动练习的映射）。

### 一次方案纠正（如实记录）

最初计划把教师"单项操作/联动操作"类别映射到学生端对应的具体练习（大车移动/联动练习等）。深入看`YardCraneLocalTrainingSession.cs`的`RequireAssessmentPolicy`后发现这个方向是错的：**"任务考核"模式在学生端强制要求`exercise`必须是`PickupWorkflow`或`DropoffWorkflow`，且`target.HasTarget`必须为`false`**——根本不走单项/联动那套数值目标系统。现在唯一被真正接到UI上的是`PickupWorkflow`（锁箱→起升→转运→落稳→解锁流程判定）一个。也就是说教师选哪个类别，今天的学生端考核机制没有对应的东西可以切换，这不是"类别到练习"的映射问题，是"考核只有一种真实机制"的事实。

### 实际实现

- 新建`YardCraneAssignedAssessmentTask.cs`（`Runtime/Training/`）：`YardCraneAssignedAssessmentTaskStore`，本机文件级别持久化（跟`YardCraneTrainingScoreRecorder`同一套`Application.persistentDataPath`+`JsonUtility`写法），只保留"当前下发的一个任务"，不是队列/历史。类注释明确写清楚：类别/项目只作为展示文字传递，不改变实际判定机制（`PickupWorkflow`）。
- `YardCraneTeacherSideShell.SaveTaskDraftNotice()`：`mode == "任务考核"`时才真正调用`Save(...)`写盘（时长按钮文本"5 min"/"10 min"/"15 min"/"20 min"解析成秒数），状态提示如实说明"判定机制固定为锁箱-起升-转运-落稳-解锁流程，类别/项目目前仅作展示文字"；`mode == "实训练习"`保持原有纯预览行为不变，这条模式目前没有学生端消费方。
- `YardCraneStudentSideShell.OpenAssessment()`：优先读`YardCraneAssignedAssessmentTaskStore.TryLoad(...)`，有则用教师配置的类别/项目/目标描述拼标题和说明文字、用配置的时长；没有（还没下发过，或教师端从未保存过）则完全回退到原来写死的默认考核，不会报错或空白。

### 实际验证

只做了大括号配平和`git diff --check`空白检查，没有编译、没有Unity Play。

### 未验证范围（如实列出）

- 教师端保存→学生端读取这条文件级别链路完全没有实测过（两个进程/两次Play之间的真实读写时序、文件路径在实际Player环境下是否如预期）。
- `taskModeButtons`/`taskDurationButtons`的按钮文本匹配（`"任务考核"`/`"5 min"`等）依赖UXML里的字面文本不被改动，没有更稳健的ID绑定，属于已知的脆弱点。

### 一次纠正：教师端没有"发布"按钮，用户指出链条逻辑有问题

用户指出上面这版实现有问题——教师端任务管理页实际是5行纯静态模板列表（编辑/删除按钮点了只弹"任务服务尚未接入"提示，`ShowTaskActionNotice`，不做真事），唯一会产生数据的是"创建训练任务"弹窗，而弹窗里原本只有"创建本机草稿"一个按钮。之前的实现把这个按钮当成了"发布"的触发点——但"创建草稿"和"发布给学生"概念上应该是两件事，用`AskUserQuestion`跟用户确认后，选择"创建弹窗里加一个真正的『发布』按钮，与『创建本机草稿』分开"。

## 闭环第二阶段：任务列表 + 成绩关联 + 考核统计页接真数据

### 背景

用户问"现在流程完善了吗"，如实回答：只做完了"发布→学生读到展示文字"这一小段，反向的"学生完成→教师看到结果"完全没做，教师端任务列表也还是5行假模板。用户提出"教师端和学生端在同一个程序里、本机运行，能不能建小型数据库，让老师发布的任务是针对本设备的任务，不管哪个学生登录都能完成"。用`AskUserQuestion`对齐两点：①不引入真正的数据库引擎(SQLite等)，用JSON文件模拟结构化存储，理由是这个场景单进程单写入者、不需要复杂查询，且项目一直坚持不引入未审查第三方二进制；②一次做完：任务列表+成绩关联+考核统计页接真数据。

### 实际实现

**数据层**：
- `YardCraneAssignedAssessmentTask.cs`从"覆盖单文件"升级成"追加列表"（`taskId`+`Save`/`TryLoadCurrent`/`LoadAll`/`TryFind`），新增`operationMode`字段（原来漏存了"本地/远程操作"选择）。
- `YardCraneTrainingSessionIdentity.cs`新增`AssignedTaskId`（同`ElapsedSeconds`/`CurrentScore`一样的"每帧/每次启动推送，销毁顺序无关"模式），在`BeginTraining()`里`Begin()`之后立刻设置（必须在`Begin()`重置之后，否则会被清空）——特意在启动那一刻捕获，不在保存那一刻重新读取，避免学生还在考核过程中教师发布了新任务导致这次运行被错误关联到新任务。
- `YardCraneTrainingScoreRecorder.cs`：`RunRecord`新增`assignedTaskId`字段；新增公开只读投影类型`YardCraneAssessmentRunSummary`+`YardCraneAssessmentRunViolationSummary`和`ListAssessmentRuns()`方法——**发现一个关键事实**：`PickupWorkflow`考核是`Unscored`，`hasScore`恒为`false`，`countsTowardResults`恒为`false`，这些记录从来不会进入`AppendToStudentIndex`维护的按学生索引——`ListAssessmentRuns()`只能扫描`TrainingScores/`目录下的原始`run-*.json`文件本身，不是走索引。

**教师端UI**：

## 补充：教师端"发布"按钮误诊 + 首页卡片接真实数据

### 背景

用户实际Play后报告"点击创建任务以后点击新建本地草稿和发布任务以及点击关闭按钮都没有功能事件"。日志里`[YC_SHELL_QUIT_IGNORED]`证明退出按钮的点击事件确实触发了——而退出按钮和创建/发布/关闭按钮的注册在同一段"全部UI节点都找到才批量注册"的初始化代码里，说明事件注册整体是成功的，问题不在"完全没注册"。基于这条推理，先怀疑是`发布给学生`按钮的CSS布局问题（`.teacher-task-editor-modal`有`overflow:hidden`，把两个按钮从"共享同一个bottom:27px"改成"上下堆叠"时没做过Unity视觉验证），把布局从堆叠改成了左右并排。

**用户实测反馈这次诊断反了**：上下堆叠没问题，左右并排才有问题——说明按钮点击本身从来没坏过，已经把布局改回堆叠。

## 补充：找到真正原因——两个同名"任务考核"UI元素造成的混淆
