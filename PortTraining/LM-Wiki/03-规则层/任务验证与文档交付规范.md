# 任务验证与文档交付规范

## 1. 分级生命周期

每个任务仍需说明实现、验证和状态，但验证深度必须与风险匹配，不能默认使用最重流程。

| 等级 | 典型改动 | 最小验证 | 文档节奏 |
| --- | --- | --- | --- |
| `L1 快速通道` | USS/UXML纯样式、文案、非逻辑素材、文档小修 | 目标文件语法、资源解析、节点契约；视觉由用户确认 | 同一批微调结束时合并记录 |
| `L2 聚焦验证` | 局部C#、单模块配置、编辑器工具 | 目标程序集或对应Harness；运行行为变化时补聚焦Play | 阶段收口时记录；微型L2可按批次合并 |
| `L3 完整门禁` | 跨场景、登录、训练状态、安全、PLC、评分、发布 | 指定Unity/目标环境中的入口到结果验证及相邻回归 | 验证后立即记录并同步稳定知识 |

执行顺序为：

1. **实现完成**：改动已经落入明确文件，代码或配置不存在已知的半写状态。
2. **验证通过**：在目标版本、目标环境中执行与风险相匹配的验证，并取得实际证据。
3. **状态更新**：按任务等级规定的节奏更新`CURRENT_STATUS.md`或当天讨论记录；必要时同步知识层、接口契约、Bug记录或规则层。
4. **任务交付**：向用户或下一位开发者报告结果、证据、限制和下一步。

任一阶段缺失时，不得把对应验证范围描述为“已完成”。L1可以交给用户预览，但在用户确认前状态应为`静态验证通过 / 视觉待验收`。

### 1.1 微任务执行预算

满足“已知入口、已有实现链、无场景/协议/安全/评分变化”的L1或L2任务，执行前锁定验收条件、预计文件和完整交付时间，并遵守：最多5个实现/验证文件、最多2次精确搜索、一次实现、一次最小验证。禁止附带重命名、重构、测试框架扩建和外部参考复查。

若文件或搜索预算超限，或预计完整交付时间超过原承诺上限1.5倍，必须先向用户报告范围膨胀和新估时，不能静默继续。微任务只在`CURRENT_STATUS.md`与当天讨论记录中选择一处记录；同批任务或实际Play验收完成后再归并为正式交接记录。

## 2. 状态定义

| 状态 | 使用条件 |
| --- | --- |
| `实现中` | 尚在修改，不能验证。 |
| `实现完成 / 待验证` | 改动已写入，但目标环境运行验证尚未完成。 |
| `静态验证通过 / 视觉待验收` | L1样式或素材改动通过静态门禁，等待用户确认实际画面。 |
| `验证失败 / 继续修复` | 已执行验证且未达到验收条件。 |
| `受阻` | 缺少设备、权限、外部服务或必要输入，并已记录阻塞证据。 |
| `已验证 / 已更新文档` | 验证达到验收条件，且相关文档已经同步；只有此状态可以作为任务完成。 |

“编译成功”“页面可以打开”“日志没有异常”不能单独等同于功能验证通过。

## 3. 每个任务必须留下的交接记录

普通L2/L3任务以及一批L1/微型L2收口时，在当天讨论记录中保留以下字段：

```markdown
## 任务：<任务名称>

- 任务状态：已验证 / 实现完成待验证 / 验证失败 / 受阻
- 目标与验收条件：
- 实现版本或协议版本：
- 修改文件：
- 验证环境：
- 验证步骤或命令：
- 验证结果：
- 关键日志或证据：
- 已更新文档：
- 未验证范围与已知限制：
- 下一步建议：
```

验证步骤必须是实际执行过的步骤，不能填写计划执行的内容。关键日志只保留能证明版本、输入、输出和结论的部分，禁止记录令牌、密码或个人敏感数据。

## 4. 验证要求

- 未修改C#时不得仅为形式要求重复编译全部C#；代码任务至少完成目标工具链的聚焦编译，涉及运行逻辑时再完成运行验证。
- Unity运动和物理任务必须使用项目指定Unity版本Play验证，并记录模型版本、PASS/FAIL日志、关键数值和主观观察工况。
- 跨软件接口必须验证成功、拒绝、超时、重复、断连和恢复路径中与本次改动相关的部分。
- UI纯视觉变化执行静态门禁并由用户验收画面；UI交互或路由变化必须从实际入口走到成功或失败回执。
- 修复Bug必须先记录可复现现象，再验证原复现路径不再出现，并检查至少一个相邻回归路径。
- 验证失败时继续修复；如果本轮必须停止，只能记录为`验证失败`或`受阻`，不能降低验收标准后宣布完成。
- Unity编辑器有未保存现场时，保留现场并将Play标记为待验证；不得默认保存、丢弃或复制整个工程规避阻塞。
- 连续两次验证被同一外部状态阻塞时应停止扩大验证范围，记录证据并等待合适的验证窗口。

## 5. 文档分层更新

- **原始资料层**：当天讨论记录保存需求、现象、修改过程和运行证据。
- **知识层**：稳定的架构、接口、业务流程、状态模型和设计结论从讨论记录整理进入LM-Wiki知识层。
- **规则层**：跨任务长期有效的开发、测试、发布和协作约束进入LM-Wiki规则层。
- Bug修复存在独立工单或Bug记录时，同时回写状态、根因、修复版本和回归证据。

## 6. Claude及其他智能体协作

- 按任务风险和文件路由读取最小上下文；连续任务不重复读取未变化的规则和历史文档。
- 不默认相信“已完成”文字；检查是否同时存在实现版本、目标环境验证和文档更新证据。
- 继续未完成任务时沿用原任务标题和版本链，禁止另建一套平行实现或重复参数标准。
- 新验证推翻旧结论时保留历史记录，并追加更正、根因和新证据，禁止静默覆盖历史。
- 交接时明确哪些是实际验证结果，哪些只是推断或待验证事项。
