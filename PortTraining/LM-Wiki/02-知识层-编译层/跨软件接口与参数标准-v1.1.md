# 港口实训平台跨软件接口与参数标准 V1.1

- 标准版本：1.1.0
- 生效日期：2026-08-28
- 适用软件：PortTraining、PortTeacher、PortGatewayService、QuayCraneSimulator、YardCraneSimulator、PortTosAdapter
- 状态：一期P0闭环修订基线
- 变更原则：破坏兼容性的修改必须升级主版本并形成架构决策记录

V1.0仅为未进入实现的审查草案，因P0闭环审查未通过而由V1.1整体替代；V1.1是首个允许生成共享代码的实现基线。从V1.1开始执行兼容性升级规则。

## 1. 标准目标

本标准统一每个软件的调用方向、传输协议、消息格式、参数命名、单位、状态、超时、幂等和错误处理。各软件可以独立开发和部署，但必须以本标准完成联调。

本标准中的“必须”是强制要求，“建议”是默认实现，“可选”仅允许在字段定义明确允许时省略。

## 2. 总体调用关系

```text
PortTeacher ──HTTP/WS── PortTrainingNodeService ──HTTP/WS── PortTraining
                                          ├────HTTP──── PortTosAdapter
                                          └──HTTP/WS── 对等NodeService

PortTraining ──Named Pipe── QuayCraneSimulator / YardCraneSimulator
PortTraining ──Named Pipe── PortGatewayService
场景EXE      ──Named Pipe── PortGatewayService
PortGatewayService ──S7 TCP── PLC
```

### 2.2 PortTrainingNodeService部署身份

`PortTrainingNodeService`是第六个必须交付的后台运行单元，不是可有可无的代码库。使用同一个程序包，以配置决定角色：

- `Authority`：部署在教师电脑或指定服务器，拥有用户、模板、工单和全局结果的最终裁决权。
- `Edge`：每台学生电脑必须安装，负责本机任务缓存、运行日志、outbox、自由练习和断网执行。
- `Coordinator`：联合作业期间由签名工单指定的某个Edge Node临时承担，只能裁定该`operationId`的协同步骤，不能修改权威工单。

同一局域网同一训练域只能有一个`Authority`。同机部署时Authority和Edge可以使用同一进程实例；多机部署时教师电脑运行Authority，各学生电脑运行Edge；没有教师电脑时两台Edge按离线授权运行，禁止自行产生新的Authority。

每个节点必须具有稳定`nodeId`、`nodeRole`、数据库Schema版本、数据目录、证书和健康检查端点。软件升级顺序为Authority先兼容升级、Edge随后升级；数据库迁移失败必须阻止服务启动并保留原数据库备份。

## 3. 传输标准

### 3.1 跨电脑业务接口

- 使用HTTP/1.1或HTTP/2承载REST JSON API。
- 使用WebSocket承载服务器主动事件。
- 正式部署必须使用HTTPS/WSS；仅`127.0.0.1`回环通信允许HTTP/WS。
- Content-Type固定为`application/json; charset=utf-8`。
- API根路径为`/api/v1`，事件路径为`/ws/v1/events`。
- 请求和响应编码统一为UTF-8，不允许GBK或系统默认编码。

### 3.2 本机进程通信

一期统一使用Windows Named Pipe，不采用Unity直连S7，也不在一期引入gRPC依赖。

管道名称：

- 学生端与场景：`pt.operation.{stationId}.{operationRunId}`。
- 学生端与Gateway：`pt.gateway.control.{stationId}`。
- 场景与Gateway：`pt.gateway.realtime.{stationId}`。

完整Windows路径由运行时转换为`\\.\pipe\{pipeName}`。`stationId`用于管道名时转换为小写，只保留`a-z`、`0-9`和短横线。

帧格式：

```text
4字节无符号小端长度 N
N字节 UTF-8 JSON
```

限制：

- 控制和业务消息最大1 MiB。
- 实时设备帧最大256 KiB。
- 长度为0、超过限制或JSON解析失败时关闭连接并记录协议错误。
- 一个连接中的`sequence`必须单调递增；重复或倒退帧不得再次执行。
- 连接成功后的第一条消息必须是`protocol.hello`，握手完成前不处理业务消息。

### 3.3 S7通信

- PortGatewayService对单台PLC只维持一条长连接。
- PLC地址、DB号、偏移、数据类型和读写权限只存在于版本化点表配置中。
- 必须批量读写连续数据区，禁止按每个点位建立独立请求。
- PLC急停、限位、控制断和硬件安全联锁始终优先，软件不得绕过。
- 真实S7库必须在目标PLC型号、固件和TIA配置上完成PoC后锁定。

## 4. 通用消息包络

除20毫秒实时帧可使用精简包络外，所有JSON消息使用以下结构：

```json
{
  "schemaVersion": "1.1.0",
  "messageType": "operation.start",
  "messageId": "f97e5a4f-4eb1-4fc6-a3f3-a3875923d71a",
  "correlationId": "2d7d7db6-41f5-440a-8143-a70125956d99",
  "operationId": "OP-20260828-0001",
  "operationRunId": "af617605-1860-45b2-a09d-e129080d168c",
  "workOrderId": "WO-QC-20260828-0001",
  "stationId": "QC-DEV-01",
  "sender": "PortTraining",
  "senderInstanceId": "c8235c35-8f83-4a51-8bf8-737964798d5d",
  "sequence": 1,
  "occurredAtUtc": "2026-08-28T10:20:30.123Z",
  "payload": {}
}
```

字段规则：

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `schemaVersion` | string | 是 | 语义化版本`major.minor.patch` |
| `messageType` | string | 是 | 小写分段名，如`scene.ready` |
| `messageId` | UUID string | 是 | UUID v4，小写带短横线 |
| `correlationId` | UUID string | 是 | 请求/响应和同一业务链关联；首条请求可等于messageId |
| `operationId` | string | 按消息 | 完整港口业务作业ID |
| `operationRunId` | UUID string | 运行消息必填 | 每次进入场景唯一，重试必须新建 |
| `workOrderId` | string | 任务消息必填 | 单岗位工单ID |
| `stationId` | string | 工位消息必填 | 部署工位ID |
| `sender` | string | 是 | 固定软件名或`PortTrainingNodeService` |
| `senderInstanceId` | UUID string | 是 | 本次进程实例ID，进程重启后改变 |
| `sequence` | uint64 | 是 | 每个连接/发送方单调递增 |
| `occurredAtUtc` | string | 是 | UTC RFC3339，精确到毫秒，以`Z`结尾 |
| `payload` | object | 是 | 消息类型对应的数据对象 |

未使用的可选字段直接省略，不使用空字符串表示“没有值”。接收方必须忽略同一主版本内未知的可选字段；未知枚举、缺少必填字段或主版本不兼容必须拒绝。

跨软件协议不得使用Unity `JsonUtility`直接序列化，因为它不能完整表达可选字段、字典和协议演进。应通过`PortTraining.Contracts`统一封装JSON序列化器。计算`snapshotHash`、`payloadHash`和`resultHash`时，先按RFC 8785 JSON Canonicalization Scheme生成UTF-8字节，再计算SHA-256，输出为`sha256:`加小写十六进制。

进程内超时、租约和数据新鲜度必须使用单调时钟计算；UTC只用于跨系统审计和排序。系统时间校准、夏令时或NTP回拨不得改变心跳超时结果。

## 5. ID、命名、时间和数值标准

### 5.1 ID

| ID | 格式 | 最大长度 | 示例 |
| --- | --- | --- | --- |
| `operationRunId`、`messageId` | UUID v4 | 36 | `af617605-1860-45b2-a09d-e129080d168c` |
| `operationId` | 大写前缀+日期+序号或外部映射值 | 64 | `OP-20260828-0001` |
| `workOrderId` | 大写前缀+机型+日期+序号 | 64 | `WO-QC-20260828-0001` |
| `taskTemplateId` | 大写前缀+业务编码 | 64 | `TPL-QC-DISCHARGE-01` |
| `studentId` | 字母数字、短横线、下划线 | 64 | `20260001` |
| `stationId` | `QC/YC-站点-序号` | 64 | `QC-LAB-01` |
| `externalTaskId` | 原系统值原样保存 | 128 | `TOS-MOVE-88217` |

外部ID和平台ID必须分字段保存，禁止用TOS任务号覆盖`workOrderId`。

### 5.2 JSON命名和数据类型

- 字段名使用`camelCase`。
- 消息类型使用小写点分隔。
- 枚举使用区分大小写的英文字符串。
- 布尔值只使用`true/false`，不使用`0/1`或`是/否`。
- 整数不使用字符串承载。
- 金额、密码和密钥不属于本期场景消息。

### 5.3 时间

- 存储和接口时间全部使用UTC RFC3339。
- UI按本地时区显示。
- 持续时长统一使用整数毫秒字段后缀`Ms`；统计时长可使用整数秒后缀`Seconds`。
- 不使用本地时间字符串进行排序、幂等或超时判断。

### 5.4 工程单位

| 含义 | 单位 | 字段后缀/示例 |
| --- | --- | --- |
| 长度、位置、高度 | m | `trolleyPositionM` |
| 线速度 | m/s | `hoistSpeedMps` |
| 角度 | degree | `spreaderSkewDeg` |
| 角速度 | degree/s | `rotationSpeedDegPerSec` |
| 质量 | kg | `grossMassKg` |
| 百分比评分 | 0～100 | `safetyScore` |
| 归一化手柄 | -1.0～1.0 | `gantryCommand` |

UI可把kg换算为吨显示，但接口中不传吨。禁止字段名缺少单位。

### 5.5 坐标和正方向

- 场景坐标采用Y轴向上。
- `gantryPositionM`正方向由`axisProfileId`定义，默认沿设备编号增加方向。
- `trolleyPositionM`默认从陆侧向海侧增加。
- `hoistHeightM`表示吊具基准点相对场景基准面的高度，越高数值越大。
- `hoistCommand`正值表示上升，负值表示下降。
- 原始Unity Transform不跨软件传输；任务位置使用业务位置编码和`sceneAnchorId`。
- 每个`sceneProfileId`必须配套坐标原点、轴正方向和业务位置映射版本。

## 7. 工单标准

### 7.1 WorkOrderSnapshot

工单是发布时不可变的执行快照。必要字段：

```json
{
  "schemaVersion": "1.1.0",
  "workOrderId": "WO-QC-20260828-0001",
  "operationId": "OP-20260828-0001",
  "taskTemplateId": "TPL-QC-DISCHARGE-01",
  "taskVersion": 3,
  "source": "Teacher",
  "authorityNodeId": "NODE-TEACHER-01",
  "authorityEpoch": 7,
  "taskCategory": "FormalOperation",
  "operationType": "VesselDischarge",
  "assignmentType": "Collaborative",
  "machineType": "QC",
  "stationId": "QC-LAB-01",
  "controlMode": "Local",
  "sceneProfileId": "QC-SCENE-V1",
  "pointMapVersion": "QC-IO-1.0.0",
  "workflowName": "船舶卸箱至AGV",
  "containers": [
    {
      "containerId": "MSCU7821046",
      "isoCode": "42G1",
      "grossMassKg": 28700
    }
  ],
  "spreaderConfiguration": {
    "size": "FT40",
    "twinMode": false,
    "guidePlateMode": "AutoByWorkflow"
  },
  "sourceLocation": {
    "type": "VesselSlot",
    "locationCode": "VSL-07/BAY-22/ROW-04/TIER-06",
    "sceneAnchorId": "vsl07-b22-r04-t06"
  },
  "targetLocation": {
    "type": "QuayLane",
    "locationCode": "QC-L03",
    "sceneAnchorId": "qc-lane-03"
  },
  "vehicle": {
    "vehicleType": "AGV",
    "vehicleId": "AGV-03",
    "laneId": "QC-L03"
  },
  "partnerStationIds": ["YC-LAB-01"],
  "scoringPolicy": {
    "policyId": "SCORE-QC-DISCHARGE",
    "version": 2,
    "policyHash": "sha256:...",
    "authoritativeScoringRequired": false
  },
  "runPolicy": {
    "maxAttempts": 3,
    "maxDurationMs": 1800000,
    "allowPause": true,
    "assistLevel": "Standard"
  },
  "publishedAtUtc": "2026-08-28T02:00:00.000Z",
  "availableFromUtc": "2026-08-28T02:00:00.000Z",
  "dueAtUtc": "2026-08-28T04:00:00.000Z",
  "snapshotHash": "sha256:..."
}
```

规则：

- `containers`数量为1或2；2个箱只允许`SpreaderSize=Twin20`且两个箱均为20尺。
- `spreaderConfiguration.size`必须与箱型和机型能力匹配；Twin20必须包含两个有顺序的20尺箱。
- 正式任务必须有源位置、目标位置和场景映射。
- 协同任务必须有`operationId`和至少一个`partnerStationIds`。
- 所有可评分任务必须锁定`scoringPolicy.policyId + version + policyHash`；排故任务还必须锁定`faultScenarioId + faultScenarioVersion + faultScenarioHash`。
- `authorityNodeId + authorityEpoch`确定工单最终裁决者；Edge不得修改这两个字段。
- `snapshotHash`按规范化JSON计算SHA-256，运行期间不得改变。
- 已运行工单不得原地修改；修改生成新的`taskVersion`和快照。

### 7.2 LocationRef

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `type` | LocationType | 是 | 业务位置类型 |
| `locationCode` | string | 是 | 可读的标准位置编码 |
| `sceneAnchorId` | string | 正式任务必填 | 映射到场景锚点 |
| `terminalCode` | string | TOS任务必填 | 码头/培训场站编码 |
| 机型位置字段 | object | 是 | 按下面的判别类型提供，不允许使用无Schema的metadata |

场景坐标不能替代业务位置编码；映射失败的TOS任务不得发布。

位置判别类型：

- `VesselSlot`：必须有`vesselVisitId`、`bay`、`row`、`tier`，可有`hatchId`。
- `YardSlot`：必须有`block`、`bay`、`row`、`tier`。
- `QuayLane/AgvLane/TruckLane`：必须有`laneId`、`laneSide`，可有`slotIndex`。
- `TrainingZone`：必须有已发布的`zoneId`。

### 7.3 OfflineExecutionGrant

允许离线执行的正式工单必须附带Authority签名的授权，不允许Edge自行把在线工单改为离线可执行。授权至少包含：

- `grantId`、`authorityNodeId`、`authorityEpoch`。
- `workOrderId`、`snapshotHash`、`stationId`。
- 允许的学生/班级范围、控制模式和最大尝试次数。
- `validFromUtc`、`validUntilUtc`、`maxActiveRuns=1`。
- `signatureAlgorithm=ECDSA-P256-SHA256`、`keyId`和`signature`。

Authority离线期间发布的撤销不能追溯否定一个在有效授权内已经开始的运行；同步后将其标记为`CompletedUnderOfflineGrant`并保留撤销冲突审计。急停维护、考核和高风险故障任务默认`offlineExecutable=false`。

### 7.4 自由练习工单

自由练习也必须先由本机Edge生成不可变`WorkOrderSnapshot`，再创建运行：

- `source=LocalPractice`、`taskCategory=FreePractice`。
- 唯一`workOrderId`，格式`FP-{stationId}-{yyyyMMdd}-{uuid8}`。
- `authorityNodeId`为本机Edge，`authorityEpoch`固定为本地练习域epoch。
- 锁定练习模板、场景、点表、吊具、辅助等级和本地评分策略版本。
- 不占用教师正式工单，不允许使用空`workOrderId`进入场景。

## 8. 生命周期标准

### 8.1 任务模板

```text
Draft → Validated → Published → Retired
```

### 8.2 工单

```text
Queued → Available → Preflight → Starting → Running
                                   ↓          ↓
                                Terminated  Paused
                                              ↓
                                           Running
Running → Completed / Terminated → Archived
Queued / Available → Cancelled → Archived
```

学生端没有人工`Accepted`状态。“任务已送达”使用自动`deliveryAck`记录，不作为学生操作。

工单状态由Authority根据运行事件投影，学生端和场景不得各自维护第二份权威工单状态。运行失败且仍有尝试次数时，工单可由Authority回到`Available`；只有原子终结事务提交成功后，工单才能投影为`Completed`或`Terminated`。

### 8.3 训练运行

```text
Created → AcquiringLease → Launching → Ready → Running → Finalizing
                                          ↓       ↓          ↓
                                        Failed  Paused   Completed / Terminated / Failed
                                                  ↓
                                               Running
```

- 外部场景返回`scene.ready`后，运行进入`Ready`。
- 学生端确认Gateway租约和场景均Ready后发送`operation.begin`，此后才进入`Running`。
- `Completed`必须有结果；`Terminated`和`Failed`必须有原因码。
- 每个工位同时最多一个非终态运行。
- `Finalizing`期间禁止重新取得运动控制；只有安全回执和结果在NodeService单事务提交后才能进入终态。

### 8.4 联合作业

```text
WaitingForParticipants
→ ParticipantsReady
→ InProgress
→ WaitingForHandover
→ HandoverConfirmed
→ Completed
```

任意阶段可进入`Paused`或`Terminated`。单个子工单完成不自动把全局联合作业标记为完成。

## 9. PortTraining与场景EXE接口

### 9.1 启动参数

学生端启动场景EXE时只传非敏感参数：

```text
--station-id QC-LAB-01
--operation-run-id af617605-1860-45b2-a09d-e129080d168c
--scene-instance-id 487cfd47-8d27-4472-8260-7e04f3ad3f4e
--coordinator-pipe pt.operation.qc-lab-01.af617605-1860-45b2-a09d-e129080d168c
--gateway-pipe pt.gateway.realtime.qc-lab-01
--gateway-lease-id 13d90675-f6cc-4382-8240-a61cac60fdf9
--display-profile DESKTOP-16X9-V1
--scene-profile QC-SCENE-V1
--protocol-version 1.1.0
```

一次性会话令牌通过受限环境变量`PORTTRAINING_SESSION_TOKEN`传递，不出现在命令行、日志或崩溃报告中。令牌为至少256位随机值。学生端在启动场景前把令牌SHA-256摘要注册给Gateway；Gateway只保存摘要。令牌完成学生端和Gateway两次握手后立即失效，最迟60秒失效。

### 9.2 消息顺序

```text
1. PortTraining向Edge Node创建运行并取得RunTicket
2. PortTraining生成sceneInstanceId和一次性令牌
3. PortTraining调用gateway.session.prepare
4. Gateway原子复核设备、锁定模式并返回Reserved租约
5. PortTraining启动scene进程
6. scene通过operation pipe发送scene.hello，PortTraining验证令牌
7. PortTraining发送operation.start（完整工单快照）
8. scene携带leaseId、sceneInstanceId、令牌和streamId连接Gateway
9. Gateway验证令牌摘要并把租约提升为Active
10. scene完成加载并发送scene.ready
11. PortTraining发送operation.begin
12. scene返回operation.started；Edge Node随后投影为Running
13. 双心跳、设备帧和operation.event持续运行
14. scene发送operation.completeRequested或terminateRequested
15. PortTraining请求Gateway安全释放；Gateway返回safeStateReceipt
16. PortTraining调用NodeService原子finalize
17. NodeService返回finalization.ack后，PortTraining允许scene退出
```

关键消息：

| messageType | 方向 | 关键payload |
| --- | --- | --- |
| `scene.hello` | 场景→学生 | sceneName、sceneVersion、machineType、supportedProtocolVersions |
| `operation.start` | 学生→场景 | workOrder、student、station、runPolicy |
| `scene.ready` | 场景→学生 | loadedSceneProfile、gatewayConnected、readyChecks |
| `operation.begin` | 学生→场景 | startedAtUtc、controlLeaseId |
| `operation.started` | 场景→学生 | sceneStartedAtUtc、gatewayStreamId、firstInputSequence |
| `operation.heartbeat` | 双向 | state、elapsedMs、lastSequence |
| `operation.event` | 场景→学生 | eventCode、severity、metrics、sceneTimeMs |
| `operation.completeRequested` | 场景→学生 | metrics、eventLogManifest、localEstimate |
| `operation.terminateRequested` | 双向 | reasonCode、reasonDetail |
| `safeStateReceipt` | Gateway→学生 | leaseId、PLC反馈序号、安全状态、Gateway签名 |
| `finalization.ack` | NodeService→学生 | terminalState、runVersion、resultRecordId |

`SceneRunEvidence`至少包含机构指标、流程节点、问题事件、场景版本和事件日志清单。事件日志采用分块上传，每个事件包含`eventId`、`eventType`、`eventSequence`、`sceneElapsedMs`、结构化`evidence`、`previousEventHash`和`eventHash`，形成哈希链。

## 10. 场景EXE与Gateway实时接口

### 10.1 protocol.hello

必须包含：

- `sessionToken`。
- `stationId`、`operationRunId`、`machineType`、`leaseId`、`sceneInstanceId`。
- 新生成的`streamId`；每次Named Pipe重连都必须改变。
- `sceneVersion`、`protocolVersion`、`pointMapVersion`。
- `requestedFrameIntervalMs`，一期默认20。

Gateway把令牌SHA-256与学生端预注册摘要进行常量时间比较，并验证租约、场景实例、机型和点表后返回`protocol.accepted`或`protocol.rejected`。握手成功后销毁令牌摘要，后续依赖租约和双心跳。

### 10.2 EquipmentInputFrame

Gateway发送给场景的实时帧：

```json
{
  "schemaVersion": "1.1.0",
  "messageType": "equipment.inputFrame",
  "operationRunId": "af617605-1860-45b2-a09d-e129080d168c",
  "streamId": "22d44ba4-18f3-49ba-8d1c-18819205cbd5",
  "sequence": 15241,
  "capturedAtUtc": "2026-08-28T10:20:30.123Z",
  "dataAgeMs": 8,
  "quality": "Good",
  "controlMode": "Local",
  "plcOnline": true,
  "emergencyStopReleased": true,
  "controlPowerOn": true,
  "handlesCentered": false,
  "gantryCommand": 0.0,
  "trolleyCommand": 0.45,
  "hoistCommand": -0.2,
  "hornPressed": false,
  "machineInputs": {}
}
```

`gantryCommand`、`trolleyCommand`、`hoistCommand`范围为`-1.0～1.0`。超界值按协议错误处理，不由场景静默截断。模拟量帧采用“最新值覆盖”，不补播断线期间的旧帧。

锁销、吊具尺寸、导板、吊具泵、复位等瞬时动作不得作为20毫秒状态字段重复发送，统一使用独立消息：

```json
{
  "schemaVersion": "1.1.0",
  "messageType": "equipment.action",
  "operationRunId": "af617605-1860-45b2-a09d-e129080d168c",
  "streamId": "22d44ba4-18f3-49ba-8d1c-18819205cbd5",
  "actionId": "077812fc-6a17-47e7-87a2-011d9f9e4d2c",
  "actionSequence": 18,
  "actionType": "SpreaderLock",
  "targetState": "Locked",
  "occurredAtUtc": "2026-08-28T10:20:30.123Z"
}
```

接收方按`operationRunId + actionId`只消费一次并返回`equipment.actionAck`。重发使用相同`actionId`；修改目标必须创建新动作。动作去重记录保留到运行归档。

动作目标约束：`SpreaderLock/Unlock`目标分别为`Locked/Unlocked`；`SpreaderSizeChange`目标为`FT20/FT40/Twin20`；`GuidePlateChange`目标为`GuidePlateMode`；`SpreaderPumpChange`目标为`On/Off`；`Reset`不携带目标值。其他组合按`CONTRACT_VALIDATION_FAILED`拒绝。

`equipment.actionAck`固定结构如下：

```json
{
  "schemaVersion": "1.1.0",
  "messageType": "equipment.actionAck",
  "operationRunId": "af617605-1860-45b2-a09d-e129080d168c",
  "streamId": "22d44ba4-18f3-49ba-8d1c-18819205cbd5",
  "actionId": "077812fc-6a17-47e7-87a2-011d9f9e4d2c",
  "actionSequence": 18,
  "status": "Accepted",
  "originalStatus": "Accepted",
  "executionPhase": "LockPending",
  "errorCode": "",
  "detail": "queued-for-fixed-step-execution",
  "occurredAtUtc": "2026-08-28T10:20:30.125Z"
}
```

- `status`只能是`Accepted | Rejected | Duplicate`。`Accepted`表示动作已通过契约与互锁检查并排入物理固定步，不等于锁销或机构动作已经完成；物理完成必须由后续反馈帧和设备事件确认。
- `Duplicate`不得再次执行动作；`originalStatus`必须保留第一次处理的`Accepted`或`Rejected`。第一次被拒绝的动作重复到达时仍然是拒绝结果，不能因为`status=Duplicate`被客户端误判为成功。
- 同一`actionId`改变`actionType`或`targetState`返回`ACTION_ID_CONFLICT`，不得覆盖第一次结果。重复消息可跨当前连接重发，但必须属于同一`operationRunId`和当前已接受的输入流。
- 动作执行前除了设备静止条件，还必须检查最后一帧小车、起升和大车控制指令已经归零，防止“速度尚为零但手柄已经给出运动指令”的一帧竞态。

### 10.3 SimulatorFeedbackFrame

场景发送给Gateway的反馈帧至少包含：

- `operationRunId`、`streamId`、`sequence`、`capturedAtUtc`。
- 大车、小车、吊具位置与速度。
- 吊具着箱、箱体连接状态。
- 四角锁销状态：`frontLeft/frontRight/rearLeft/rearRight`。
- 吊具尺寸和机型专属状态。
- 当前安全状态、报警代码和任务阶段。

Gateway只允许向点表白名单写入反馈字段。评分和训练档案字段不得写入PLC。

### 10.4 数据新鲜度和失联

| 项目 | 默认值 | 处理 |
| --- | --- | --- |
| PLC批量轮询目标 | 20ms | 记录实际周期 |
| 实时帧目标 | 20ms | 始终消费最新帧，不积压旧控制帧 |
| 数据警告阈值 | 100ms | 标记`Stale`并告警 |
| 数据危险阈值 | 250ms | 撤销运动授权并进入安全处理 |
| 场景心跳间隔 | 500ms | 双向发送 |
| 场景心跳超时 | 2000ms | Gateway清零控制、学生端终止运行 |
| 学生端所有者心跳 | 500ms | PortTraining向Gateway续租 |
| 学生端所有者超时 | 2000ms | Gateway进入SafeHold并清零控制 |
| 学生协调器心跳 | 1000ms | 场景与学生端互检 |
| 学生协调器超时 | 5000ms | 场景暂停并请求安全退出 |
| 场景Ready超时 | 120s | 启动失败，可由管理员配置 |
| Gateway连接超时 | 5s | Preflight失败，不启动任务 |

安全阈值可按现场联调收紧，但不能由普通学生修改。

所有超时由接收进程的单调时钟计算。Named Pipe重连后使用新`streamId`并从`sequence=1`开始；接收方不得把新流序号与旧流比较。场景心跳或学生端所有者心跳任意一方超时，Gateway立即进入`SafeHold`，停止接受动作并输出安全默认值。安全条件恢复只允许进入复位检查，Gateway和场景不得据此自动退出`SafeHold`；还必须收到操作者新的显式故障复位请求、确认手柄回中和机构静止，并且不得回放旧控制帧。

## 11. PortTraining与Gateway控制接口

关键消息：

- `gateway.status.get` / `gateway.status`：版本、PLC在线、点表、周期、数据年龄和故障。
- `gateway.preflight.request` / `gateway.preflight.result`：仅用于UI诊断，不作为最终安全授权。
- `gateway.session.prepare` / `gateway.session.prepared`：在Gateway单一临界区内重新读取设备帧、验证版本/急停/电源/手柄/台位、锁定模式、注册`sceneInstanceId + tokenHash`并返回Reserved租约。
- `gateway.session.activate` / `gateway.session.active`：场景令牌验证成功后把Reserved租约提升为Active。
- `gateway.owner.heartbeat`：PortTraining每500ms续租。
- `gateway.lease.release` / `gateway.lease.released`：正常释放。
- `gateway.safeStateReceipt`：Gateway依据PLC反馈确认安全状态并使用设备证书签名。
- `gateway.safetyEvent`：急停、失联、模式变化、点表错误。
- `gateway.incident.list` / `gateway.incident.ack`：PortTraining或Edge Node恢复后补取Gateway持久化事故记录。
- `gateway.shutdownSafe`：安装维护时安全退出，不允许运行中调用。

控制租约字段至少包含`leaseId`、`leaseEpoch`、`operationRunId`、`stationId`、`sceneInstanceId`、`controlMode`、`preflightInputSequence`、`issuedAtUtc`、`expiresAtUtc`。同一工位只能有一个`Reserved`或`Active`租约。

`gateway.session.prepare`请求必须包含`operationRunId`、`ownerInstanceId`、`sceneInstanceId`、`sessionTokenHash`、`workOrderSnapshotHash`、`controlMode`、`sceneVersion`、`pointMapVersion`和请求租约时长；不得包含原始会话令牌。`safeStateReceipt`必须包含租约、运行、PLC反馈序号、安全输出值、确认时间、Gateway版本、点表版本、`keyId`和签名。

正常完成顺序为“场景停止运动命令 → Student请求释放 → Gateway写入安全默认值 → PLC反馈确认 → Gateway签发`safeStateReceipt` → NodeService原子终结”。场景自报的安全状态不具有终结效力。若PLC无法确认安全，运行进入`FailedSafetyUnconfirmed`并触发Critical告警，不得伪装为正常完成。

所有修改接口必须支持`Idempotency-Key`请求头。资源更新使用`expectedVersion`或`If-Match`，版本冲突返回HTTP 409。`RunTicket`至少包含`operationRunId`、`createdByNodeId`、`authorityNodeId`、`authorityEpoch`、`workOrderSnapshotHash`、`runVersion`和签名。

`finalization`是唯一允许把运行写入终态的接口。服务端必须在一个数据库事务内完成：验证`expectedVersion`、验证全部证据块哈希、验证Gateway安全回执、计算或确认评分、写入最终结果、更新运行终态、更新工单投影并写入可靠outbox。任一步失败则全部回滚。

Gateway调用`gateway-incidents`时使用本机设备证书或受ACL保护的回环凭据；Gateway自己的durable outbox必须保留事件，直到Edge返回相同`incidentId`的持久化确认。

### 12.2 WebSocket事件

事件类型：

- `workOrder.published`、`workOrder.updated`、`workOrder.cancelled`。
- `station.statusChanged`。
- `run.stateChanged`、`run.safetyEvent`、`run.resultCommitted`。
- `collaboration.stateChanged`、`handover.requested`、`handover.confirmed`。
- `teacher.terminateRequested`。

WebSocket断开后，客户端必须使用最后`eventCursor`调用`GET /api/v1/events`补拉，不能假定断开期间没有事件。Authority至少保留90天游标事件；Edge至少保留到所有outbox被Authority确认后30天。游标过期返回`EVENT_CURSOR_EXPIRED`，客户端必须执行全量投影同步。

### 12.3 权威与离线同步

- 在线创建正式运行时，由Authority检查工单和当前活动运行后生成`operationRunId`。
- 离线时，Edge只有持有效`OfflineExecutionGrant`才能生成`operationRunId`，并把`createdByNodeId`和授权快照写入本地不可变运行日志。
- 正式任务离线结束后，Edge在本地原子finalization并设置`syncState=PendingAuthority`，UI显示“已完成待同步”；只有Authority确认后才变为`AuthorityCommitted`并影响教师端权威档案。
- 自由练习由本机Edge担任该本地练习工单的Authority，终结后使用`syncState=LocalOnly`；联网后可上传副本，但不要求中央裁决。
- Edge只追加运行事件和证据，不修改Authority工单快照、authorityEpoch或历史结果。
- `POST /sync/outbox`按`messageId`和`operationRunId`去重；Authority收到同一运行的相同哈希返回已接受。
- 同一工单出现两个不同活动运行时，优先接受符合更高`authorityEpoch`的运行；同一epoch下按有效授权、开始时间和站点绑定裁决，另一运行标记`ConflictQuarantined`，不得自动计入档案。
- Authority在Edge离线期间撤销任务时，不追溯否定已经依有效授权开始的运行；未开始的授权在Edge收到撤销后立即冻结。
- 所有冲突保留双方事件，不以“最后写入覆盖”解决。

## 13. TOS标准接口

PortTosAdapter提交`StandardExternalOrder`，至少包含：

- `externalSystem`、`externalTaskId`、`externalVersion`、`payloadHash`。
- 作业类型、设备号、箱号/箱型/重量。
- 船名、航次、Bay/Row/Tier或堆场Block/Bay/Row/Tier。
- AGV/集卡号、源车道和目标车道。

## 14. 对等Edge Node接口

无教师电脑的两学生机联合作业使用PT-IF-010：

- `peer.hello`：节点ID、软件版本、工位和能力。
- `collaboration.offer`：operationId、两个子工单快照哈希、协调节点。
- `collaboration.join`：参与工位和学生会话摘要。
- `participant.ready`：本机Preflight结果。
- `handover.request` / `handover.confirm`：箱体交接。
- `collaboration.heartbeat`：每1000ms。
- `collaboration.pause` / `collaboration.resume` / `collaboration.terminate`。
- `collaboration.result`：子结果哈希和全局完成状态。

协调节点必须由Authority签名的联合作业工单预先指定，并携带`coordinatorNodeId + coordinationEpoch`。两个Edge Node不组成多数派，网络分区时禁止自动选主或自行增加epoch。

- 任一参与节点连续5秒收不到对方心跳，双方都必须进入`Paused`，禁止确认箱体交接。
- 原协调节点恢复后，以原epoch继续；需要更换协调节点时，必须由Authority签发更高epoch，或终止旧运行并创建新运行。
- 无Authority在线且原协调节点不可恢复时，本次联合作业保持暂停，只允许教师现场授权终止，不允许另一节点自行完成。
- `handover.confirm`必须同时引用QC子运行、YC子运行、车辆状态版本和箱体交接证据哈希。

HTTP错误结构：

```json
  "error": {

    "message": "workOrder.sceneProfileId is required",

    "retryable": false,
    "details": [
      { "field": "sceneProfileId", "reason": "required" }
    ]
  }

```

| `PLC_OFFLINE` | PLC离线 | 是 |
| `CONTROL_MODE_MISMATCH` | 台位模式与任务不符 | 条件修复后可重试 |
| `CONTROL_LEASE_CONFLICT` | 工位已有活动租约 | 否，先回收旧运行 |

| `INPUT_STREAM_MISMATCH` | 消息不属于当前握手接受的streamId | 新流完成握手后可重试 |
| `INPUT_SEQUENCE_REJECTED` | 实时帧或动作序号倒退、重复 | 否，丢弃旧消息 |

| `MECHANISM_NOT_READY` | 场景机构尚未初始化完成 | 等待Ready后重试 |
| `MECHANISM_BUSY` | 机构处于预张紧、载荷交接或其他互斥阶段 | 阶段结束后创建新动作重试 |

## 16. 幂等、并发和持久化

- 创建工单、运行、迁移、证据上传和终结必须有幂等键。
- 状态迁移携带`expectedVersion`，服务端使用单事务比较并更新。
- 终结以`operationRunId`为唯一键，首次成功提交后不可覆盖；终态、结果、工单投影和outbox同事务提交。
- 本地JSON原型不得用于多进程生产写入；NodeService和Gateway使用SQLite或等价事务存储，并启用崩溃恢复和Schema迁移。
- Edge采用durable outbox补传Authority；只有Authority确认后才能删除，删除前至少保留30天审计记录。
- Gateway把租约、安全事件和安全回执写入独立事故日志；PortTraining崩溃不能造成事故记录丢失。
- 文件型离线包使用“写临时文件 → 刷盘 → 原子替换”，并保存SHA-256与发行方签名。
- 每个外部事件保留`messageId`去重记录；保留期限不少于任务最长离线周期。

## 17. 安全标准

- Named Pipe设置Windows ACL，仅允许当前交互用户、受信服务账号和管理员访问。
- 一次性会话令牌不得写入日志、命令行、工单或训练结果。
- LAN正式部署使用HTTPS/WSS；访问令牌包含角色、学生/教师ID、工位范围和过期时间。
- TOS连接使用独立服务账号，建议mTLS或目标系统认可的强鉴权。
- 密码、API密钥和证书不得存入`StreamingAssets`、源码或普通JSON配置。
- 教师终止、任务修改、模式变更、配置变更和结果冲突必须写审计日志。
- 外部系统指令永远不能绕过急停、限位和PLC硬件安全链。
- Authority保存Argon2id或不低于当前组织安全基线的加盐密码摘要，不保存明文或可逆密码。
- Edge离线登录使用Authority签发、限定学生/班级/工位/有效期的离线身份凭据；凭据过期后只能进入明确允许的本地自由练习。
- LAN HTTPS证书由项目本地CA或院校PKI签发，安装程序负责建立信任；禁止通过“忽略证书错误”完成部署。
- SceneManifest、PointMapManifest、离线任务包和评分规则使用`ECDSA-P256-SHA256`签名，并通过`keyId`支持密钥轮换。

## 18. 配置标准

### 18.1 StationProfile

必须包含：

- `stationId`、`displayName`、`machineType`。
- `deploymentMode`、`supportedControlModes`。
- `taskNodeEndpoint`。
- `gatewayControlPipe`、`gatewayRealtimePipe`。
- `plcProfileId`、`pointMapVersion`。
- `sceneProfileId`、`displayProfileId`、`inputProfileId`、`axisProfileId`。
- `allowSimulationFallback`。

`allowSimulationFallback`在正式考核工位必须为`false`。

### 18.2 NodeProfile

必须包含`nodeId`、`nodeRole`、`trainingDomainId`、监听端点、Authority地址、数据库路径、数据库Schema版本、证书引用、事件保留期和outbox策略。私钥和密码只保存为Windows证书/凭据存储引用，不直接写入配置。

### 18.3 SceneManifest

必须包含场景名称、可执行文件版本、支持机型、协议版本、场景配置版本、最低Gateway版本、显示配置、文件SHA-256、签名算法、`keyId`和签名。学生端启动前先验证签名和文件哈希。

### 18.4 PointMapManifest

必须包含PLC型号、固件基线、Rack/Slot、DB版本、读取区、白名单写入区、数据类型、缩放、死区、语义字段、默认安全值、配置SHA-256和发行方签名。

## 19. 兼容与发布规则

- `1.x`接收方必须忽略未知可选字段。
- 增加可选字段升级次版本；修正文档或不影响语义的缺陷升级补丁版本。
- 删除字段、修改类型/单位/枚举语义、改变状态机均升级主版本。
- 连接握手交换支持版本范围，未找到共同主版本立即拒绝。
- 每个发布包记录学生端、教师端、场景、Gateway、协议、点表和配置的兼容矩阵。

## 20. V1.1联调验收用例

1. 教师端创建并发布QC卸船工单，学生端自动同步且不需要点击接收。
2. 学生点击进入驾驶室，NodeService生成唯一`operationRunId`，Gateway先注册令牌摘要并原子锁定模式，场景完成双握手后Ready。
3. 20毫秒设备帧连续运行；Named Pipe断开重连后生成新`streamId`，旧流不会阻塞或污染新流。
4. 同一锁销动作重发三次只执行一次；使用相同`actionId`改变目标返回`ACTION_ID_CONFLICT`。
5. 场景完成后重复调用finalization两次，只生成一条训练记录。
6. finalization数据库事务中途强制崩溃，重启后不会出现终态与结果不一致。
7. 使用同一运行ID提交不同结果，系统返回`RESULT_CONFLICT`且不覆盖首个结果。
8. 场景进程崩溃，2秒内Gateway撤销控制并清零安全输出。
9. PortTraining进程崩溃但场景仍运行，2秒内Gateway因所有者心跳丢失进入SafeHold。
10. Running期间切换Local/Remote，Gateway原子租约失效，运行暂停或终止。
11. PLC反馈无法确认安全时，运行进入`FailedSafetyUnconfirmed`，不能标记Completed。
12. 教师端离线后，学生凭有效OfflineExecutionGrant完成任务；恢复连接后结果只补传一次。
13. 无效、过期或站点不匹配的离线授权不能创建正式运行。
14. 两台学生机网络分区后双方暂停，参与节点不得自行提升为协调节点。
15. Authority签发新coordinationEpoch后，旧协调节点停止裁定，箱体交接只确认一次。
16. 自由练习先生成LocalPractice工单快照，完整走运行、终结和档案流程。
17. 事件日志缺块或哈希链断裂时，正式考核不生成权威分数。
18. WebSocket断线后通过eventCursor补拉事件；游标过期时执行全量同步。
19. SceneManifest、点表或协议版本/签名不匹配时明确阻止启动。
20. 篡改离线任务包、评分规则或场景EXE后，签名或哈希验证失败并记录审计。

以上二十项通过后，V1.1接口才具备进入多软件并行开发的条件。
